# 后端分层架构

本文件是课程 RAG 项目的离线评估语料，用来固定一份可复现的知识基准。它不是运行时上传的用户资料。

## Router 层的职责

Router 层只负责接收 HTTP 请求。它解析路径参数、查询参数和请求体，然后调用 Service 层。

Router 层不应该承载业务逻辑。把分支判断和流程编排堆进 Router，接口会变得难以阅读和测试。

Router 层也不直接访问数据库。它不编写 SQL，也不关心表结构和索引。

一个健康的 Router 函数通常只有几行：取出入参、调用一次 Service、把领域结果转换成响应模型。

Router 层负责的另一件事是路由声明。它决定路径、HTTP 方法、状态码和响应模型。

判断 Router 是否过重有一个简单办法：把 Web 框架换掉时，需要重写的代码越少越好。

## Schema 层的职责

Schema 层使用 Pydantic 描述请求和响应的数据形状。它声明字段名、类型、默认值和取值范围。

Pydantic 校验发生在 Service 之前。字段类型不合法时 FastAPI 直接返回 422，Service 层根本不会被调用。

Schema 层只做结构校验，不做业务校验。库存是否充足属于业务规则，应该留给 Service 层判断。

请求模型和响应模型建议分开定义。共用同一个模型容易把内部字段暴露给外部调用方。

字段级校验器适合处理修剪空格、统一大小写这类清洗工作。它让 Service 拿到的数据已经规整。

响应模型同时承担文档职责。它决定 OpenAPI 里展示的字段，也决定实际序列化出去的字段。

## Service 层的职责

Service 层负责业务逻辑。它判断订单状态、计算金额、决定工作流程并编排多个数据操作。

Service 层不知道 HTTP。它不返回状态码，只返回领域结果，或者抛出领域异常。

Service 层通过 Repository 读写数据。它不直接拼接 SQL，也不感知具体数据库方言。

如果有人问业务规则应该写在哪里，答案通常是 Service 层，而不是 Router 层或 Repository 层。

Service 层是最值得写单元测试的一层。它的输入输出是纯粹的领域数据，不需要启动 Web 服务。

一个 Service 方法应该对应一个明确的用例。方法名描述业务动作，而不是描述数据库操作。

## Repository 层的职责

Repository 层负责数据访问。它封装查询、新增、更新和删除这四类基本操作。

Repository 层向上暴露领域对象。调用方不需要知道底层是 PostgreSQL 还是内存字典。

Repository 层不做业务判断。它不决定订单能否退款，只负责把订单取出来或写回去。

把数据访问集中在 Repository 层，替换存储实现时受影响的范围会明显缩小。

Repository 层适合定义查询方法的语义边界。找不到记录时返回 None，还是抛出异常，应该全项目统一。

## 依赖注入

依赖注入让上层接收依赖，而不是自己创建依赖。Service 在构造时接收一个 Repository 实例。

依赖注入最直接的好处是可测试。测试可以传入 Fake Repository，不需要启动真实数据库。

FastAPI 使用 Depends 声明依赖。请求到达时，框架负责解析依赖并把实例注入处理函数。

在构造函数里直接 new 一个具体实现，会把上层和下层焊死，单元测试只能连真实资源。

依赖注入也让配置集中。数据库连接、超时时间和外部客户端可以在应用启动时统一装配一次。

依赖注入不等于必须引入容器框架。手工在启动入口装配对象，同样是依赖注入。

## HTTP 异常映射

领域异常在 Service 层抛出，由统一的异常处理器映射成 HTTP 状态码。

异常映射应该集中在一处。Service 抛出 OrderNotFound，处理器把它映射成 404 响应。

对外的错误消息必须保持稳定。它不暴露堆栈、内部路径、配置值或数据库细节。

同一类失败要返回同一个错误码。让前端可以按错误码分支，而不是靠解析中文文案。

参数校验失败返回 422，资源不存在返回 404，冲突返回 409，上游服务失败返回 502。

在每个 Router 函数里写 try except 是常见反模式。它把同一段映射逻辑复制到几十个地方。

## FastAPI 分层原则

依赖方向自上而下。Router 依赖 Service，Service 依赖 Repository，反向依赖会破坏分层。

每一层只做一件事。职责混在一起时，一个需求变更往往要同时改动多个层。

分层的目的不是让文件更多，而是让变更的影响范围可预测。

层与层之间通过明确的数据结构通信。跨层直接传递框架对象会让下层被 Web 框架污染。

分层是一种成本。项目非常小的时候，过早分层同样会拖慢开发速度。

判断分层是否合理，可以看测试写起来是否顺手。需要启动整个应用才能测一条规则，说明层次没有分开。
