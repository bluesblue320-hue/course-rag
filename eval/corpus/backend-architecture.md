# 后端分层架构

## Router 层

Router 层是 HTTP 入口，负责接收请求、读取路径参数和查询参数、解析请求体，并把处理结果转换为 HTTP 响应。Router 只做参数传递，不直接操作数据库，也不实现业务规则。例如创建用户的接口只负责把请求体交给 Service，Service 返回结果对象后，Router 负责设置状态码并返回响应。把大量业务逻辑堆进 Router，会让参数解析、校验和规则混在一起，代码难以阅读，也难以单独测试。

## Schema 层

Schema 层定义请求和响应的数据结构。本项目使用 Pydantic 模型描述输入输出：请求模型负责解析和校验客户端数据，响应模型保证返回字段稳定。Schema 层可以做字段级校验，例如字符串长度、数字范围、枚举取值，但不应包含需要查询数据库才能判断的规则。请求数据在进入 Service 之前先经过 Pydantic 校验，非法数据会被拒绝并返回 422，Service 层不需要反复防御脏数据。

## Service 层

Service 层承载核心业务逻辑，例如校验业务状态、计算价格、协调多个数据操作。Service 不依赖 HTTP 细节，也不知道请求来自浏览器还是命令行。Router 调用 Service，Service 调用 Repository，方向固定，不允许反向依赖。业务规则放在 Service 层之后可以独立测试，不需要启动 Web 服务器。如果有人在网上问业务逻辑应该写在哪里，通常的答案是 Service 层。

## Repository 层

Repository 层封装数据访问，负责查询、新增、修改和删除记录。Service 只依赖 Repository 的接口，不直接编写 SQL，也不关心底层是 PostgreSQL 还是内存列表。Repository 返回领域对象，避免把数据库细节泄漏到上层。更换存储实现时，只需要替换 Repository 的实现类，其余层级不需要改动。

## 依赖注入

依赖通过构造函数注入到类中，而不是在类内部自行创建。例如 Service 构造函数接收 Repository 实例，测试时可以传入假的 Repository 来验证业务规则。显式注入让依赖关系可见，也让替换实现变得容易。依赖注入与接口配合使用，是分层架构可测试性的基础。

## HTTP 异常映射

领域异常和 HTTP 状态码分离。Service 抛出领域异常，例如资源不存在，Router 层或全局异常处理器负责把它映射成 404。这样业务代码不依赖 Web 框架的状态码，更换框架时业务逻辑不用重写。异常映射集中在一处，也让响应格式保持一致，不会出现同一个错误在不同接口返回不同状态码。

## 分层原则

依赖方向只能从外层到内层：Router 依赖 Schema 和 Service，Service 依赖 Repository 和领域对象，内层不 import 外层。统一的分层让每个关注点都有明确归属：接口形状归 Schema，规则归 Service，数据归 Repository。分层不是越细越好，过度的分层会增加样板代码，但把职责明显不同的代码混在同一层，长期维护成本更高。
